# 07. OpenMausBot as the foundation

Source: shallow clone of https://github.com/milind-soni/OpenMausBot, commit `ccbe58b` (2026-11-14), version 0.1.158 (`package.json:4`). Every `path:line` below is relative to that clone. Nothing was run and nothing was fetched. A claim marked (doc) rests on a docs page only; the rest was read in code.

## The question

Can OpenMausBot replace OpenBot as the base of SEO in a Box v1: an Operator connects a client's Site, directs five Bots from the Workbench, every Ship step waits for Approval and is recorded in Activity, one Instance per client, and the Bots follow the 30 SEO skills as Agent Skills folders?

## Short answer

OpenMausBot fixes most of what was wrong with OpenBot. The whole server is in the public repository under Apache 2.0, it runs without any account or licence key, it serves its own web UI from a container, it loads Agent Skills folders with their scripts, and it has Bots, group rooms, Routines, an approval log and CSV export. It is not a drop-in for our core promise, though. Its approval model is the opposite of ours: the default level is Full access, an approval is the engine's own permission mode passed through, browser and computer-use actions are pre-allowed and never ask, nothing in the open-source edition can lock a level, and on a default self-hosted server a Bot's shell counts as the owner of the server's own API. It also has no Site, no Deliverables and a single maintainer shipping more than one release a day. Verdict: a workable foundation to fork, with the Ship-step gate, the Site model and the Workbench built by us on top, and two hardening switches (`OMB_BOT_BOX=1`, `OMB_LOOPBACK_TRUST=service`) treated as mandatory.

### 2. What must run, and where

- It runs as a server reached from a browser, no desktop app needed: the server serves its own UI (`server/index.ts:185`, `server/index.ts:12564`) and the docs list what runs headless: every engine, chats, rooms, routines, connected apps, webhooks and the Bots' browser (doc: `docs/self-hosting.md:189-208`). Desktop-only: dictation and controlling the host's own desktop (doc: `docs/self-hosting.md:210-212`).
- Services: one Node 24 process (`package.json:19-21`) that listens on loopback, plus Caddy for TLS, joined by Unix sockets (`deploy/docker-compose.yml:1-10`, `deploy/docker-compose.yml:34-44`). The container runs as an unprivileged user with `HOME=/data` (`Dockerfile:235`, `Dockerfile:19-21`), with an init and 512 MB of shared memory for Chrome (`deploy/docker-compose.yml:29-30`). Neither `deploy/docker-compose.yml` nor `compose.yaml` sets `privileged`, `cap_add` or `security_opt` (searched).
- Storage is files in one data folder: SQLite `messages.db` and `runtime.db`, per-thread event logs, `bots.json` (doc: `docs/sentinel.md:29-32`, `docs/runtime-contract.md:25`), `routines.json` (`server/routines.ts:329`), `config.json`, and the `decisions/` log (`server/decision-log.ts:2`). Engine logins live in the same volume (doc: `docs/self-hosting.md:421-422`). No external database.
- Required secrets: none to start. A provider key is written once with `openmausbot engine set claude --key-env ANTHROPIC_API_KEY` (doc: `docs/headless-cli.md:262-279`); sign-in lists and SMTP come from environment variables (`deploy/docker-compose.yml:45-53`).
- Shapes: `npx openmausbot serve` behind an existing proxy, with a built-in Caddy, over Tailscale or on a LAN (doc: `docs/self-hosting.md:24-31`); Docker Compose with Caddy, described as "One tenant = one container" (doc: `docs/self-hosting.md:365`); a one-command Ubuntu installer (doc: `docs/self-hosting.md:121-136`); rootless Podman (doc: `docs/self-hosting.md:354`); many workspaces on one host with `fleet` (section 3). What each gives up: the npm path ships no engine tools or browser, which are installed separately (doc: `docs/self-hosting.md:221-222`), while the image bakes them in (doc: `docs/self-hosting.md:402-403`); the `--tunnel` shape needs an OpenMausBot account (doc: `docs/self-hosting.md:30`).
- Bot computers: a Bot's `computer` is `cloud`, `vm`, `local`, `browser` or off (`packages/phone-protocol/src/wire.ts:69`, `packages/phone-protocol/src/wire.ts:306`), and cloud means Boat or a VPS (`packages/phone-protocol/src/wire.ts:66`). Boat is a third-party service (`README.md:274`). A VPS desktop needs an SSH user in the `docker` group, which the docs call root-equivalent (doc: `docs/byo-vps.md:41-44`). A Local VM uses the host's Docker socket (doc: `docs/bot-box.md:72`). The Docker image ships the Bots' browser (doc: `docs/self-hosting.md:202-204`); on a bare Ubuntu 24.04 host its sandbox needs an administrator step (doc: `docs/deploy-vps.md:239`).
- Upgrades: self-hosted servers follow a `stable` channel, a release the project's own cloud has run for 48 hours (doc: `docs/deploy-vps.md:341-349`). `update.sh` copies the data, starts the new version and rolls back if it is unhealthy (doc: `docs/releasing.md:99-119`). Data rule: what version N writes, N-1 can read, enforced by a format marker (`CONTRIBUTING.md:110-125`, `server/data-format-released.json:1-5`). Apps promise to work with any server that was stable in the last 90 days (doc: `docs/deploy-vps.md:612-617`).

### 3. Tenancy

- Two session scopes, `admin` and `client` (`server/sessions.ts:19`); a client session is default-deny with an explicit allow-list (`server/request-auth.ts:304-305`). Email sign-in lists map to them: admins get full access, members "chat and approvals only" (doc: `docs/self-hosting.md:822-826`, `docs/self-hosting.md:838-841`). A People screen lists and invites (doc: `docs/self-hosting.md:874-880`).
- Inside one deployment: sidebar departments (`packages/phone-protocol/src/wire.ts:347`), a Chief of Staff per department (`packages/phone-protocol/src/wire.ts:351`), and per-Bot visibility by person or domain (doc: `docs/self-hosting.md:913-925`).
- Several clients in one deployment is not safe. Every Bot's shell runs as the same OS user (doc: `docs/self-hosting.md:752-756`), "A bot's shell can still read files on the server" (doc: `docs/self-hosting.md:975-976`), and engine logins, keys and the server's config are shared.
- One deployment per client is the documented shape (doc: `docs/self-hosting.md:365`). For many on one host, `openmausbot fleet` gives each workspace its own OS user, systemd unit, ports, data folder, sign-in list and provider key behind the system Caddy (`server/fleet.ts:1-2`, doc: `docs/self-hosting.md:512-543`), with create, suspend, upgrade and delete commands and an audit log (doc: `docs/self-hosting.md:524-551`). No entitlement check was found in the fleet command-line code; the Settings screen for it is gated (`server/routes/status.ts:85-87`), and a workspace's `brand.json` is written (`server/fleet.ts:384`) but applied only with the whitelabel entitlement (`server/brand.ts:78-80`).
- Owner, Admin and Member roles with private conversations belong to the hosted Team Cloud (doc: `docs/team-cloud.md:9-13`).

### 4. A Bot's computer

- Shell and files: the engine's own tools, run on the server in a per-conversation folder (`server/workspace.ts:14`) or a folder set on the Bot (`packages/phone-protocol/src/wire.ts:315`). By default this is the server's own user and filesystem.
- The bot box is a bubblewrap sandbox for each turn: it hides the data folder, other Bots' folders and other processes, limits loopback to capability routes and sends traffic through an egress gate (doc: `docs/bot-box.md:3-6`, `docs/bot-box.md:12-19`, `docs/bot-box.md:30-37`). It is on by default only in the hosted cloud; elsewhere it needs `OMB_BOT_BOX=1` and working user namespaces (`server/bot-box/detect.ts:63-72`).
- Browser: each Bot gets its own isolated, persistent session (doc: `docs/self-hosting.md:202-204`). A person can take the browser over; the hold ends two minutes after their last view closes or five minutes after their last input (`server/browser/hold.ts:12`). Docs disagree on whether live watching has shipped: "the next step" (`docs/self-hosting.md:205`) against "implemented, pending release" (`docs/plans/browser-engine.md:90`).
- Desktop: Local VM modes are shared, per-Bot or pool (`server/config.ts:485`); a VPS gives one container per Bot (doc: `docs/byo-vps.md:3-5`); "Take control" opens the live desktop in a paired admin browser (doc: `docs/self-hosting.md:1032-1040`).
- Time limits: a turn silent for 20 minutes is stopped, or 2 hours while a tool runs (`server/index.ts:4979-4980`); a room turn has 5 minutes by default (`server/config.ts:46-48`); a routine has an optional run limit (`server/routines.ts:992-993`); an idle Local VM stops after 480 minutes (`server/local-vm-settings.ts:18`).

### 5. Approvals

- The levels are `ask`, `edits`, `auto`, `full` and `custom` (`packages/phone-protocol/src/approval-mode.ts:5`). The default is Full access (`packages/phone-protocol/src/approval-mode.ts:75`). Ask becomes the default only on a "hosted workspace" (`server/index.ts:768`), which is switched on by `OMB_ADMIN_*` settings (`server/enterprise.ts:71-73`) and refuses remote access without the paid `admin` entitlement and a separate identity service (`LICENSING.md:17-19`, `enterprise/README.md:88-95`).
- The design is pass-through: "Nothing here decides whether an action is safe: each level is the provider's own permission mode passed through" (`server/auto-approve.ts:1-4`). The docs say the same: "Approval cards are the provider's own ... OpenMausBot adds none" (`docs/self-hosting.md:892-893`). The project's design rules forbid new asks and any default below Full access (`DESIGN.md:52-54`). The README headline "Bots ask before they act" (`README.md:147-150`) describes the Ask level, not the default.
- Claude engine: the level maps to Claude Code's `default`, `acceptEdits`, `auto` or `bypassPermissions` (`server/drivers/claude.ts:1001-1005`). Below Full, Claude Code's permission prompts are routed to the server's broker and become cards (`server/drivers/claude.ts:1145-1147`). At Full the flag is not passed and nothing asks.
- What asks at the Ask level on Claude: commands and file changes, "the way the provider's supervised mode does" (doc: `docs/approval-levels.md:35`), and tools of custom MCP servers, which are never pre-allowed (`server/drivers/claude.ts:1117`). Which commands count is Claude Code's decision, not the server's.
- What never asks, at any level, on Claude: the built-in browser, the Bot's cloud or VM computer, the server's own agents tools and the connected-apps bridge are passed in `--allowedTools` (`server/drivers/claude.ts:1074`, `server/drivers/claude.ts:1083`, `server/drivers/claude.ts:1089`, `server/drivers/claude.ts:1100`, `server/drivers/claude.ts:1159`). A form posted or a purchase made through the browser is recorded but not gated.
- Connected-app sends have the one gate the server owns. Tool names containing send, post, publish, pay, buy and similar verbs count as outbound (`packages/phone-protocol/src/outbound.ts:14-35`, `packages/phone-protocol/src/outbound.ts:93-104`), and the Composio relay holds them behind a "Send on your behalf?" card (`server/index.ts:14407-14416`, `server/outbound-hold.ts:52-76`). The rule is per Bot, `ask` or `allow` (`packages/phone-protocol/src/outbound.ts:8-11`). At Full access a Bot with no stored rule sends without asking (`server/outbound-hold.ts:33-37`). The match is by tool name, so a write that is not a send, such as creating a pull request or updating a page, is not held by it.
- API-key engines (OpenAI-compatible and others) use the server's own tool gate, which reads the level before each call (doc: `docs/approval-levels.md:63-65`); a card there times out as a denial after 15 minutes (`server/drivers/chat-tool-approval.ts:68`).
- Third-party CLI engines keep the mode they were started with until the turn ends (doc: `docs/approval-levels.md:66-72`). In their permissive modes they never send a request, so the server sees nothing to gate: "It cannot reach an engine that never asks" (`server/safety-floor-gate.ts:1-4`).
- How rules are expressed: the level per Bot and per conversation (`packages/phone-protocol/src/wire.ts:319`); saved exact commands (`packages/phone-protocol/src/wire.ts:321`); remembered read-only MCP tools (doc: `docs/approval-levels.md:168-177`); per-app read or write scopes and the outbound rule (`packages/phone-protocol/src/wire.ts:365-366`); an allow and deny list of tools (`packages/phone-protocol/src/wire.ts:388`).
- Who can change them. An admin session can set any Bot to Full: "Full access applies from any client that can reach this API" (`server/routes/bot-patch.ts:509`). A chat-only session may change only display fields of a Bot (`server/request-auth.ts:512-519`), but the conversation route is on its allow-list (`server/request-auth.ts:363`) and accepts `approvalMode`, refusing Full only on a cloud home or hosted workspace (`server/routes/tasks.ts:272-275`, `server/routes/tasks.ts:378-384`); no scope check was found there. On a default self-hosted server a request from the machine itself has the admin scope (`server/request-auth.ts:30`, `server/request-auth.ts:110`), and every Bot's shell is such a caller (`server/request-auth.ts:11-13`), so a Bot could raise its own level; the docs say as much: Full access can be turned on by "a bot or script calling the local API where local calls count as you" (`docs/approval-levels.md:42-45`). `OMB_LOOPBACK_TRUST=service` closes that except for gaps the code itself lists (`server/request-auth.ts:33-40`).
- Can named kinds of action always ask, with no Operator override? No mechanism was found. The nearest things: hosted-workspace mode refuses Full access (`server/routes/bot-patch.ts:519-522`) but is an enterprise feature; the safety floor is a never-list of destructive shell commands that an environment variable can force on (`server/safety-floor-gate.ts:14-17`), is off by default, and does not cover engines in their permissive modes (doc: `docs/verification/safety-floor.md:118-123`); organisation policy restricts engines, MCP servers, apps and computers, not approvals (`server/managed-policy.ts:7-24`).
- Unattended runs: an approval raised by a scheduled run waits, the notification names the routine, and the run stops with "Stopped: nobody answered the approval" if the wait runs out (`server/routine-waits.ts:56`, doc: `docs/routine-schedules.md:93-100`). A held send times out after 9 minutes and is refused (`server/outbound-hold.ts:13`, `server/outbound-hold.ts:100-103`). The log marks decisions made with nobody at the keyboard (`server/decision-log.ts:68-69`). A run at Full access asks nothing.
- The Bot API for outside callers always runs confined and at Ask, and nobody outside can approve (doc: `docs/bot-api.md:52-54`, `docs/bot-api.md:68-73`).

### 6. Activity

- Decision log: one append-only NDJSON file per month under `decisions/`, mode 0600, secrets redacted (`server/decision-log.ts:2-4`). Each row has time, thread, Bot, tool, summary, the rule, whether it was unattended and who answered (`server/decision-log.ts:53-74`). Kinds cover automatic approvals and denials, cards shown, and a person's approve, deny or undo (`server/decision-log.ts:15-23`).
- Admin activity: who changed which setting, person, session, webhook, MCP server, engine or Bot, with before and after values (`server/admin-activity.ts:1-3`, `server/admin-activity.ts:13-31`). It is kept only on a workspace several people share (doc: `docs/self-hosting.md:1297-1300`, `docs/self-hosting.md:1318-1319`).
- Per-Bot activity: tool runs from the event logs joined with decisions, with outcomes ran, failed, running, allowed, denied and waiting (`server/routes/status.ts:230-243`, `packages/phone-protocol/src/activity.ts:5-17`). So actions that ran without asking are recorded too.
- Viewing and export: `GET /api/decisions`, `/api/decisions.csv`, `/api/admin-activity` and its CSV, filtered by date, kind and person (`server/routes/status.ts:177-227`); a Settings Activity screen (doc: `docs/self-hosting.md:1321-1323`); an Activity panel per Bot (`src/components/ActivityPanel.tsx:29`).
- Retention: 180 days by default, 1 to 3,650 by config or environment (`server/decision-log.ts:81-82`, `server/decision-log.ts:95-101`). Event logs of long-closed conversations are swept separately; transcripts are kept (`server/thread-retention.ts:1`).

### 7. Skills

- Native Agent Skills: "Per-bot Agent Skills: imports keep their whole folder" (`server/skills.ts:1`). `SKILL.md` needs frontmatter with `name` and `description` (`shared/skill-md.ts:88-99`). Sibling files come in up to 200 files, 16 MB, 2 MB each, depth 8; hidden files, links and `node_modules` are skipped (`server/skill-folder.ts:14`, `server/skill-folder.ts:24-34`). Scripts keep their executable bit (`server/skill-folder.ts:190`).
- Install: `POST /api/bots/:id/skills` with a GitHub or skills.sh URL or `owner/repo` (`server/routes/bot-skills.ts:69-80`). Discovery walks the path, then its child folders and their children, up to 30 skills per import (`server/skill-fetch.ts:215-217`, `server/skill-fetch.ts:238-285`). The SEO repository's `category/skill/SKILL.md` layout fits that walk.
- Imports land disabled; a person enables each one per Bot (`server/routes/bot-skills.ts:30`, `server/routes/bot-skills.ts:89-108`). A shared skills library exists behind a feature switch (doc: `docs/feature-flags.md:56`) but its import route takes `SKILL.md` text only (`server/routes/bot-skills.ts:154-171`). The team file likewise seeds a single `SKILL.md` per skill (`server/headless/team-apply.ts:254-257`).
- Through which engine: enabled skills are linked into `.claude/skills`, `.agents/skills` and `.grok/skills` of the working folder, where Claude Code, Codex and Grok load them themselves (`server/skills.ts:336`, `server/skills.ts:381-385`), and every engine also gets a prompt index naming each `SKILL.md` path (`server/skills.ts:1255-1276`). The index is capped at 30 skills and 4,000 bytes (`server/skills.ts:50-51`); the rest are found with a `skills_list` tool (`server/drivers/agents-catalog.ts:794`).
- Invocation: the model picks a skill from the index, or a turn starting with `/skill-name` runs it; "The very start of a turn's text can call one, whoever wrote it" (`shared/skill-command.ts:1-7`), so a Routine's instructions can name a skill. A scheduled run uses the Bot's enabled skills like any turn.
- The 30 SEO folders: all have `name` and `description`, 27 are a lone `SKILL.md`, two carry a script and one an examples file, all far inside the limits (measured in the SEO skills clone). Two caveats. Five use a folded YAML description (`description: >-`), and the parser is "Deliberately not a YAML engine" and reads one line per key (`shared/skill-md.ts:85-87`, `shared/skill-md.ts:118`), so the server's own index would show `>-` for those; the engine's native loader still reads the file. And 30 descriptions, most of 250 to 500 characters, exceed the 4,000-byte index, so most would be listed only natively or through `skills_list`. Several skills also expect outside API keys or MCP servers (Ahrefs, DataForSEO, OpenRouter), which is a credentials question (section 10), not a loading one.

### 8. Bots, models and working together

- A Bot has a name, title, standing instructions (`soul`), a model selection that names an engine instance and model, a level, a computer, a folder, tool and app scopes and skills (`packages/phone-protocol/src/wire.ts:263-388`). A YAML team file declares teams, Bots, rooms, skills and engine keys and is applied idempotently (doc: `docs/headless-cli.md:282-300`, `docs/headless-cli.md:325-360`).
- Engines: Claude Code, Codex, Grok, Cursor, Gemini, Qwen, OpenCode and other CLIs, plus API engines for OpenAI-compatible endpoints, OpenRouter, xAI, Mistral, Groq and more (doc: `docs/approval-levels.md:260-274`).
- Authentication. A saved Anthropic API key runs every Claude Bot, with nobody signing in (doc: `docs/self-hosting.md:486-490`; `server/config.ts:459-460`; `server/drivers/claude.ts:986`). The Claude engine is still the `claude` command-line tool started in stream mode (`server/drivers/claude.ts:1025-1030`), so that tool must be installed in the image (`deploy/.env.example:5-7`). API engines need only a key. Codex "has no key path by design and always uses a personal ChatGPT login" (doc: `docs/self-hosting.md:494-495`). Consumer subscription logins are supported and described as a normal path (doc: `docs/self-hosting.md:559-575`), but nothing requires them.
- So running on API keys alone is supported for Claude and the API engines, not for Codex.
- Working together: rooms with several Bots and a responder rule (doc: `docs/headless-cli.md:355-360`), delegation with the `coordinate_bots` tool (`server/drivers/agents-catalog.ts:239`), a Chief of Staff whose level flows down to delegated work (`server/auto-approve.ts:39-60`), and a job record for every hand-off (doc: `docs/runtime-contract.md:1-22`).
- External agents: any CLI that speaks ACP over stdio plugs in by config (doc: `docs/custom-engines.md:24-41`); custom MCP servers by URL or command (doc: `docs/custom-mcp-servers.md:1-17`); OpenMausBot is itself an MCP server for orchestration, which "intentionally cannot approve requests" (doc: `docs/mcp-server.md:1-15`). AG-UI: not found.

### 9. Routines

- Schedule types: cron with a time zone, once, weekly, interval, and limit-reset (`server/routine-request-schemas.ts:24-41`); fields include instructions up to 20,000 characters, a run limit, overlap `skip` or `queue`, and run on startup (`server/routine-request-schemas.ts:43-53`). Webhook triggers and app events are separate (`README.md:430-460`).
- API: `GET` and `POST /api/routines`, `PATCH /api/routines/:id`, `POST /api/routines/:id/run` (`server/index.ts:14515-14544`). Bots create them with a `trigger` tool (`server/drivers/agents-catalog.ts:672`). The team file has no routines section (`docs/headless-cli.md:325-360`), so seeding is by API call.
- Limits and history: stored in `routines.json`, the last 2,000 runs kept (`server/routines.ts:285`, `server/routines.ts:329`); one missed occurrence is caught up within 12 hours and overlapping copies do not pile up (doc: `docs/routine-schedules.md:87-92`); a failed unattended run is retried once (doc: `docs/routine-schedules.md:101-108`). The scheduler runs inside the server process only (doc: `docs/routine-schedules.md:78-81`).

### 10. Connected apps and credentials

- Connected apps are Composio sessions; GitHub is among them (doc: `docs/composio.md:1-9`). A server run from source registers only with an explicitly named service, so a self-hosted Instance needs its own Composio project key (doc: `docs/composio.md:27`, `docs/composio.md:81-89`). Composio is a third party that holds the OAuth grants.
- WordPress: no connector or MCP entry found; the word appears only in a hosting-suffix list, an app-name list and a word pattern (`shared/site.ts:23`, `shared/today-outcomes.ts:37`, `src/lib/automations.ts:205`). It would be a custom MCP server or our own tool.
- Custom MCP servers, by URL with headers or by command with environment variables (doc: `docs/custom-mcp-servers.md:11-17`). Values are write-only in the UI but "persist as plaintext in the 0600 config file" (doc: `docs/custom-mcp-servers.md:557-564`).
- Readable by the Bot? By default yes: "Files the server's user owns (`config.json`, the engine's environment) are also still readable from a bot's shell" (doc: `docs/self-hosting.md:812-814`).
- With the bot box on, a secret can be usable but unreadable. The data folder is not in the box (doc: `docs/bot-box.md:14`); Anthropic, OpenAI and Gemini keys are replaced by per-process tokens and injected by a broker outside the box, and URL MCP headers travel the same way (doc: `docs/bot-box.md:84-93`); connected apps are reached with a per-turn bearer (doc: `docs/bot-box.md:107-108`). Not covered: keys for CLIs with no base-URL setting (doc: `docs/bot-box.md:110-112`), subscription logins (doc: `docs/bot-box.md:74-75`), and a command-type MCP server, which runs inside the box with its variables.
- A vault hands a Bot a secret as a one-use reference bound to the Bot and conversation, or as an owner-only file, masked in transcripts (`server/secret-vault.ts:1-6`).
