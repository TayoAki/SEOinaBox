# Research 02: how Bots run the SEO skills

Written 2026-11-14 from local clones of `CopilotKit/OpenBot` and `Illyism/seo-skills` (plugin version 1.3.0), read offline. Nothing was run. Each claim is followed by its source as `openbot:path:line` or `seo-skills:path:line`. The OpenBot server's source is not in the clone, so anything about server behaviour comes from its docs, the app code and the harness code, and is marked where it could not be confirmed.

## The question

What is the most workable way to make OpenBot Bots carry out the 30 SEO skills, with every Ship step still passing OpenBot's approval gate and landing in Activity? Three options:

- **A.** Convert each `SKILL.md` into an OpenBot skill (instruction text in the tenant package's `skills.yaml`).
- **B.** Keep the `SKILL.md` folders as files in the Bot's workspace, and give each Bot short OpenBot skills that say "read and follow this file".
- **C.** Run the Bots on the Claude Agent SDK harness (`agent-claude-sdk`), in the hope that it loads `SKILL.md` folders natively.

## Short answer

**Choose B, and take the Ship steps out of the shell.** Define the five Bots in the tenant package as `built-in` Bots, which carry a `system_prompt` and a `skills:` list (openbot:docs/configuration.md:1273-1287). Keep a pinned copy of the SEO skills in each Bot's workspace, and give each Bot one short OpenBot skill per SEO skill. Do pull requests and CMS drafts through an app tool (GitHub, WordPress), never through `git push` or `curl` in the shell.

The main reason is that B is the only option in which the SEO skills, their two scripts and their `seo/` state folder work as written while every action still goes through OpenBot's gateway, which decides against policy and writes the Activity row before anything happens (openbot:docs/architecture.md:42-48). Three findings carry the decision:

1. **C does not do what was hoped.** The harness deliberately removes Claude Code's own tools and keeps only `Read` (limited to its own saved tool results) and `ToolSearch` (openbot:agent-claude-sdk/src/adapter.py:804-831, openbot:shared/harness-own-tools.ts:11-14). There is no `Skill` tool and no settings source for a full Bot, so no native `SKILL.md` loading. Turning those tools back on would run them "in this container instead, ungoverned and unapproved" (openbot:agent-claude-sdk/src/adapter.py:805-810).
2. **A Bot's own computer is not gated by default.** Shell commands and file writes there "don't ask unless Extra vigilant, Auto-review or a rule says so" (openbot:docs/approvals.md:104-106). So a `git push` or a `curl` POST from the shell would be recorded but would not raise an Approval. This holds for A, B and C alike, and is why the Ship steps must move to app tools, which are granted, decided against policy and recorded per call (openbot:docs/architecture.md:333).
3. **A is weak exactly where the daily Routine needs it.** An OpenBot skill's text reaches the Bot when a person picks it with `/` at the start of a message (openbot:app/src/lib/plugins/skill-commands.ts:17-27). A Routine's instruction is wrapped in three fixed sentences before it is sent (openbot:shared/routine-firing.ts:9-13, 52-54), and nothing in the clone shows a Routine invoking a skill. With B the Routine's instruction can name the file to read.

## Facts

### 1. OpenBot skills

- A written skill is five fields: `slug` (2 to 40 lower-case letters, digits and hyphens), `title` (up to 120 characters), `summary` (up to 200, optional), `instructions` (required, no maximum in the form) and `tools`, a list of `serverId/toolName` refs (openbot:app/src/lib/skills/form.ts:15-49). The form says its limits "match the server's parser exactly" (openbot:app/src/lib/skills/form.ts:7-9), so no length limit on instructions is evidenced. The server parser itself could not be read.
- No limit on the number of skills was found. The largest instruction shipped in the example package is about 7 KB (`skill-creator`, openbot:examples/fintech/skills.yaml:103-106). The 30 `SKILL.md` files run from 1.8 KB to 17.5 KB and total about 309 KB (measured with `wc -c` on the clone).
- The public API spec does not cover skills. It defines Bots and reactions only (openbot:api/openapi.yaml:40, 93, 221). Skills are saved through `POST /api/plugins/skills` (openbot:docs/architecture.md:343).
- A package skill becomes a deployment skill at start-up, visible to everybody in the `/` menu (openbot:docs/configuration.md:1415). A package Bot lists the skills it carries under `skills:` in `agents.yaml` (openbot:docs/configuration.md:1285-1287). A person's own skill can go only on Bots they own, and administrators manage deployment skills (openbot:docs/architecture.md:327).
- A skill is "an instruction rather than a capability": naming a tool grants nothing, and what a Bot is offered is always intersected with what it was granted (openbot:docs/configuration.md:1419, openbot:docs/architecture.md:353).
- Tool narrowing: a Bot holding more than twelve tools is offered, per run, only the tools of the skills that match the message, plus every granted tool no skill claims. The deployment's own model does the matching, and every failure leaves the whole catalogue offered (openbot:docs/configuration.md:1417, openbot:docs/architecture.md:349-355). Past fifty tools, an app's tools wait behind `search_tools` unless a chosen skill asked for them (openbot:docs/architecture.md:359).
- A written skill cannot carry files or scripts: the form has no such field (openbot:app/src/lib/skills/form.ts:15-49). A second kind of skill can. Skills that CopilotKit Intelligence learns from conversations and recordings are published as a `SKILL.md` plus other files (openbot:shared/learning.ts:94-98, openbot:app/src/components/learning/skill-files.tsx:5-9) and a Bot loads them with `copilotkit_load_skill` and `copilotkit_read_skill_file` (openbot:tests/learning_harness_contract.py:21-22). The docs describe these only as proposals from Intelligence's Learning agent that a person approves (openbot:docs/automatic-learning.md:29). Whether a hand-written `SKILL.md` folder can be put into that channel is not shown.

### 2. The Bot's computer

- Tools, by name (openbot:app/src/lib/copilot/computer-tools.tsx:313-329):
  - Browser: `computer_navigate`, `computer_read`, `computer_snapshot`, `computer_type`, `computer_click`, `computer_key`, `computer_scroll`. The Bot takes a snapshot that lists every field and button with a ref, then types and clicks by ref (openbot:shared/bot-prompt.ts:88-97).
  - Handing over to a person: `computer_request_help` (the person takes the browser), `computer_request_secret` (one masked value typed straight into a field) and `computer_request_sign_in` (a private sign-in form; the Bot "never see[s] the username, password or code") (openbot:shared/bot-prompt.ts:109-126, openbot:app/src/lib/copilot/sign-in-tool.tsx:33).
  - Files: `computer_list_files`, `computer_read_file`, `computer_write_file`. Paths are relative to the Bot's workspace and nothing outside it is reachable. Writes are text only (openbot:app/src/lib/copilot/computer-tools.tsx:707-711, 754-758, 878-882). A file read returns up to 64,000 bytes (openbot:agent-claude-sdk/src/adapter.py:191), which covers every `SKILL.md`.
  - Shell: `computer_run_command` runs bash in the workspace. Python 3 with pip, Node.js, Bun, curl and "the usual Linux tools" are installed, `pip install` works, and `apt-get install` works as root or through `sudo openbot-apt` (openbot:app/src/lib/copilot/computer-tools.tsx:796-812). Git is not named in that list, so its presence is unconfirmed.
- The shell is one live bash per Bot and person, so `cd` and exported variables carry over, and a process started with `&` keeps running (openbot:CHANGELOG.md:2228-2233). A command has a 120 second default limit and a 600 second maximum (openbot:CHANGELOG.md:8313-8317).
- The workspace is `/workspace` on the computer (`WORKSPACE_DIR`, openbot:docs/configuration.md:933) on a named volume (openbot:docker-compose.yml:321-323), and it "survives between conversations" (openbot:shared/bot-prompt.ts:99). With one computer per person, each Bot has its own folder and browser profile in it, and an Isolated Bot gets a container of its own (openbot:docs/architecture.md:91). On a shared computer, `COMPUTER_SEPARATE_WORKSPACES` gives each Bot its own folder, though "commands can still read other folders" (openbot:docs/configuration.md:838). The folder's absolute path is not documented, so an OpenBot skill should name files by workspace-relative path.
- So a Bot can in principle `git clone`, run Node scripts and install packages (openbot:README.md:384). Outbound connections from the browser and the shell pass a filter proxy that applies the Bot's network policy: `allow_all`, `defaults_plus_allowlist`, `allowlist_only` or `deny_all` (openbot:docs/architecture.md:93). What the defaults allow was not found.
- Credentials. The vault holds saved logins and keys; apps and the browser draw on it and "a Bot never sees what is in it" (openbot:docs/how-openbot-works.md:105-112). Stored credentials are either model keys or connector keys (openbot:app/src/lib/credentials/form.ts:7-12). No path from the vault into a shell command is documented. A command inherits only PATH, locale, terminal and proxy variables; `COMPUTER_SHELL_ENV` passes extra names, and "naming a secret ... there is an operator's decision" (openbot:docs/configuration.md:945-948). A Bot can run anything on its computer, root included (openbot:docs/architecture.md:87), so a token passed that way is readable by the Bot.
- A push or pull-request token can therefore be kept from the Bot only by not putting it in the shell. The route that does this is a GitHub app: through Composio "the account does not live here", the broker holds it (openbot:docs/plugins/composio.md:3-9), and a Shared app is one account connected once by an administrator, such as "a company GitHub bot" (openbot:docs/plugins/composio.md:497-500).

### 3. Approvals and policy

- Two separate controls apply to every action. The action policy ("boundaries") is a list of CEL rules that refuse or permit. Deny is evaluated before allow, and the shipped default is `deny: []`, `allow: ["true"]` (openbot:docs/architecture.md:69-76). Approvals decide what stops to ask a person. Admin has a "what would happen" page that runs the real deciders on a described action in order: grant, app allowlist, capabilities, network, boundaries, safety, approvals (openbot:shared/what-if.ts:99-107, openbot:README.md:348).
- CEL fields: `tool.name`, `intent`, `bot.id`, `actor.id`, `page.url`, `page.host`, `element.ref`, `element.role`, `element.name`, `element.type`, `key`, `command`, `file.path`, `file.name`, `file.extension`, `mcp.server`, `mcp.tool`, `mcp.effect`, `initiator.kind`, `initiator.id` (openbot:docs/architecture.md:50-67). `initiator.kind` is `person`, `deployment`, `routine`, `responsibility`, `memory` or `handoff`, and is the only field that tells an unattended run from somebody typing (openbot:docs/architecture.md:62-67, 108-115).
- What asks is decided in this order, first answer wins: kinds of action, then rules (the strictest matching rule wins, and a team rule that asks beats anything a member allowed), then Auto-review, then the person's Extra vigilant switch (openbot:docs/approvals.md:3-14).
- The kinds that ask in every edition are deleting, sending, sharing, posting or publishing, paying, and changing credentials or security settings. They are recognised by an app tool's first verb, an app's destructive marker, a button's label, or payment words on the page (openbot:docs/approvals.md:6-9, 39-44, 79-94). They are open by default, meaning a person may answer "Always allow here"; an administrator can set a kind to "Ask every time" or "Members do it themselves" (openbot:docs/approvals.md:59-65). `how-openbot-works.md` still says paying "is always handed to you" (openbot:docs/how-openbot-works.md:88-90), which `approvals.md` says was reversed (openbot:docs/approvals.md:53-55).
- How the four actions in question are classified:
  - **Shell command** (`run_command`) and **file write** (`write_file`) on the Bot's own computer: through the gateway and recorded, matchable in CEL by `command` and `file.*`, but left out of the safety asks (openbot:shared/what-if.ts:31-41, openbot:app/src/components/approvals/ask-first-copy.ts:10-13).
  - **Browser form submit**: asks only if the button is labelled Send, Share, Post, Publish, Delete, Pay and the like. "Submit" is not on the list, and "Confirm" or "Done" are named as not recognised (openbot:docs/approvals.md:39-44, 112-116). A shipped CEL template, "Never submit a form", refuses it outright (openbot:app/src/lib/boundaries/rules.ts:20-31).
  - **MCP write**: the grant is checked, then the policy with `mcp.*`, then the call is recorded (openbot:docs/architecture.md:333). It asks if its name starts with one of the kinds' verbs or its app marks it destructive. Otherwise it is "an ordinary change, which asks only when Extra vigilant or a rule says so" (openbot:docs/approvals.md:94-96).
- An approval rule has five fields: `botId`, `toolRef` (examples given: `composio-gmail/*`, `computer_click`, `host/*`), `effect` (`*`, `write`, `read`), `scope` (a target: `*`, an app, a site, a folder, a Bot name) and `behaviour` (`allow`, `pre_approved`, `ask`, `hand_off`) (openbot:app/src/lib/approvals.ts:14, 42-48, openbot:app/src/components/approvals/describe-rules.tsx:46-60, openbot:app/src/components/approvals/rules.tsx:331-336). There is no field for a command pattern.
- Gating `git push` specifically. Three mechanisms are evidenced, and none is "ask before this one command":
  1. A CEL deny rule built from the documented fields, for example `tool.name == "computer_run_command" && contains(command, "git push")` (openbot:docs/architecture.md:52, 59, 69). It refuses, it does not ask, and it is a string match that a script file would get around.
  2. An approval rule with `toolRef: computer_run_command`, `behaviour: ask` for one Bot. On the evidence of the rule's fields this would ask before every command that Bot runs.
  3. Keep the push out of the shell. Give the shell no write credential, and open the pull request with a GitHub app tool under a rule such as `toolRef: <github app>/*`, `effect: write`, `behaviour: ask`. Making an app Shared adds exactly such a team rule by itself: "Writes ask first" (openbot:docs/plugins/composio.md:533-534).
- Gating a CMS write specifically. Through an app tool, the same rule shape on the CMS app. Through the browser, a button labelled Publish already asks (openbot:docs/approvals.md:44), a rule with `toolRef: computer_click` and the Site as `scope` asks before every click there, and CEL can refuse by `page.host` and `element.name`.
- In a Routine nobody is watching, but "OpenBot will still ask the person before anything it gates" (openbot:shared/bot-prompt.ts:488-494). The request waits in the approvals inbox and the server carries the conversation on once it is decided (openbot:app/src/lib/approvals.ts:156-161).

### 4. The Claude Agent SDK harness and remote Bots

- Wiring: a FastAPI service on port 4212 that serves AG-UI at `/` for a full Bot and `/model` as a model-only endpoint (openbot:agent-claude-sdk/src/main.py:64-75, openbot:agent-claude-sdk/Dockerfile:13). The server proves itself with `MANAGED_AGENT_TOKEN` in the `x-openbot-agent-token` header (openbot:agent-claude-sdk/src/main.py:21, 49-56). It pins `claude-agent-sdk==0.2.152` and `ag-ui-claude-sdk==0.1.5` (openbot:agent-claude-sdk/requirements.txt:1-2).
- Tools: every OpenBot tool in the run (computer, apps, Routines, `run_subagent`) is wrapped as a tool of one in-process MCP server named `ag_ui`. Claude Code calls it, the call is handed to OpenBot to run, and the result is put back through a hook (openbot:agent-claude-sdk/src/adapter.py:588-617, 742-766). The harness runs only `ToolSearch` and `Read` itself, and `Read` is refused for any path outside the session's saved tool results (openbot:agent-claude-sdk/src/adapter.py:647-677, 820). A test pins this: `options.tools == ["Read", "ToolSearch"]` (openbot:agent-claude-sdk/tests/test_model_mode.py:144).
- Filesystem skills: searching `adapter.py`, `main.py` and `replay.py` for skills, setting sources, plugins and working directory finds only `setting_sources = []` on the model-only path (openbot:agent-claude-sdk/src/adapter.py:781). The full-Bot path sets none. OpenBot's own skills still reach it: the server writes a picked skill's instructions into the system prompt (openbot:agent-claude-sdk/tests/test_slash_text_reaches_model.py:35-38).
- Model and provider: Anthropic only. Exactly one of `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` (a Claude plan) must be set (openbot:agent-claude-sdk/src/main.py:24-41, openbot:shared/harnesses.json:117-128). The server chooses the model and effort per run (openbot:agent-claude-sdk/src/adapter.py:309-325). The harness has no row in the shared provider spec (openbot:docs/configuration.md:211-212).
- Governance kept: everything the Bot does through OpenBot's tools is granted, decided and recorded as for a built-in Bot. Governance lost: nothing in the shipped harness, because it has no tools of its own that act. If the harness were changed to enable Bash, Edit or the Skill tool, those would act inside the harness container, outside policy, Approvals and Activity. OpenBot tells such a Bot so: "Tools of your own that OpenBot did not give you are not covered" (openbot:shared/bot-prompt.ts:396-412, openbot:docs/approvals.md:74-77).
- A `remote-ag-ui` Bot in general:
  - It can use OpenBot's computer through the gateway, since the browser and file tools arrive in each run's `tools` (openbot:examples/pydantic-ai-bot/README.md:8-11). It can call granted app tools back through the server with `AGENT_TOOL_TOKEN` (openbot:docs/configuration.md:140-143). It can hand work to other Bots and ask the person, through a signed callback under the same grants, caps and records (openbot:docs/architecture.md:302-310).
  - It gets no `system_prompt` from the package. Its `role_description` is "the only instruction it ever receives from the package" (openbot:docs/configuration.md:1289-1292), and through the API that field is capped at 1000 characters (openbot:api/openapi.yaml:696). The deployment adds the standing working rules (openbot:docs/coworkers.md:42-50). It must consume forwarded context itself to use learned skills (openbot:docs/automatic-learning.md:107).

### 5. Multi-bot work and Routines

- Handing work on: `message_bot` is offered beside a Bot's granted tools, and which Bot may ask which is a grant, off until made (openbot:docs/architecture.md:228-234). The grant is directional, set by an administrator on the Bot's Setup page under "Bots it can ask", and the personal edition does not show it (openbot:docs/configuration.md:662-666). The asked Bot runs as the same person with its own grants, and its answer lands in the asking Conversation under its own name (openbot:docs/architecture.md:254-263).
- Caps: `BOT_HANDOFF_MAX_DEPTH` defaults to 1 and `BOT_HANDOFF_MAX_PER_RUN` to 3; both refuse rather than truncate (openbot:docs/configuration.md:651-660). One Bot asking the other four in a single run needs the second raised to 4.
- A group conversation can hold several Bots, each with a thread of its own and a shared transcript, and a Bot that names a peer as `@Name` hands on to it under the same grant and caps (openbot:docs/architecture.md:186). Within one Bot, `run_subagent` starts up to five fresh copies per answer, and a copy that reaches an action needing approval hands it back (openbot:shared/subagent.ts:11-14, openbot:shared/bot-prompt.ts:321-336).
- Routines: every Bot has the Routines tools in every edition (openbot:docs/routines.md:61-66). A Routine fires at most every 15 minutes, and a person may have at most 20 switched on (openbot:docs/routines.md:106-115). It runs as the person who made it, with that person's grants (openbot:docs/routines.md:182-190). Ten failures in a row switch it off (openbot:docs/routines.md:119-122). It needs the separate worker process (openbot:docs/routines.md:146-150). A run with no browser attached is given the computer tools server-side (openbot:docs/architecture.md:135-137).
- Gaps: a tenant package cannot ship Routines, and there is no administrator view of other people's Routines (openbot:docs/routines.md:199-203).
- Verdict: five role Bots plus a daily Routine are supported. The Routines have to be created after start-up, by the Operator or through `POST /api/routines` (openbot:docs/routines.md:42).

### 6. MCP

- A custom server is added by address under Connections, "Add server". OpenBot probes it: a plain MCP reply is added at once; a `401` with an OAuth challenge starts per-person sign-in with dynamic client registration; a `401` with no sign-in asks for a key, which is the server's own and, in the team edition, only an administrator may give (openbot:docs/plugins/mcp-by-url.md:3-12). Addresses must be https, not an IP literal and not internal (openbot:docs/plugins/mcp-by-url.md:34-38). With "Only approved servers" on, an administrator approves each address first (openbot:docs/plugins/mcp-by-url.md:44-49).
- Governance: administrators add and switch on every app and grant its tools per Bot. A Bot's owner may do so only where an administrator opened that app to owners (openbot:docs/architecture.md:326). Every call checks the grant, evaluates the action policy with MCP context, and is recorded (openbot:docs/architecture.md:333).
- Read or write: "unknown tools and custom-server tools are treated as writes unless positively classified as reads" (openbot:docs/architecture.md:329). A tool that carries MCP's `destructiveHint` asks as deleting does (openbot:docs/approvals.md:91-94).
- Whose credential: a catalogue entry is either deployment-wide (one key for everybody, as the keyed search providers are) or `user-oauth` (each person's own account, as Google Drive and Notion are). An administrator enabling an app and a person connecting their account are separate decisions (openbot:docs/architecture.md:331, openbot:docs/web-research.md:5-16). Per-person tokens are encrypted in the vault (openbot:docs/plugins/mcp-by-url.md:21-23).
- Composio is a broker for a few hundred apps behind one deployment key, `COMPOSIO_API_KEY`. Each person consents at Composio and a Bot reaches the app as the person asking, unless the app is made Shared (openbot:docs/plugins/composio.md:3-9, 31-36, 497-500). Nothing arrives switched on: an administrator enables an app, then grants actions per Bot (openbot:docs/plugins/composio.md:220-232). The vendor-side grant stays as wide as Composio's app asks for; OpenBot's grants are "the entire narrowing" (openbot:docs/plugins/composio.md:705-710). Arcade can be the broker instead (openbot:README.md:392).
- The three servers in the SEO skills' `.mcp.json` are plain https addresses: `aiseotracker.com/api/agent/mcp`, `scribiz.com/mcp`, `awesome.tools/mcp` (seo-skills:.mcp.json:1-16). AI SEO Tracker uses browser OAuth with no static key (seo-skills:seo/aiseotracker/SKILL.md:37-41). Scribiz and Awesome Tools need no key to start (seo-skills:content/scribiz/SKILL.md:30, seo-skills:seo/awesome-tools/SKILL.md:120). Ahrefs and DataForSEO are reached by "the official MCP server" or by REST with `$AHREFS_API_KEY`, or `$DATAFORSEO_LOGIN` and `$DATAFORSEO_PASSWORD` (seo-skills:seo/ahrefs-research/SKILL.md:19-25, seo-skills:seo/dataforseo-serp/SKILL.md:19-26, 35). `OPENROUTER_API_KEY` is read from the environment by one script (seo-skills:content/seo-blog-images/SKILL.md:90).

The Ship steps fall into five kinds. Each needs its own rule, and a CMS site needs a substitute for the first.

1. **Repo change** (16 SEO skills, counting the two where it is optional). On a Git site: a pull request opened through the GitHub app tool, under an ask rule. On a CMS site: a draft saved through a CMS app tool or the Bot's browser, with publishing left to a person. All sixteen work on the Site's own files. The link-graph script, for one, walks `app`, `pages`, `content`, `src` and `components` (seo-skills:seo/internal-linking/scripts/internal-link-graph.mjs:7), so a CMS site needs an exported copy of its content in the workspace. `block-ai-scrapers`, the redirect config in `domain-migration` and the scaffolded routes have no CMS form.
2. **Files only** (11). Plans, state and drafts under `seo/` or `marketing/`, or text in the Conversation. Nothing leaves the computer, so no rule is needed. On a CMS site the `seo/` folder needs a home that is not the Site.
3. **Submission to a third party** (2). A form, a JSON API, a registry publish or a pull request to someone else's repository. In the browser a "Submit" button does not ask by default, and from the shell nothing asks, so this kind needs an explicit rule, or the MCP route where one exists.
4. **Checkout link** (1, and optional in 2 more). The SEO skills never pay: they hand a link to a person. OpenBot also asks on payment words in the browser (openbot:docs/approvals.md:39).
5. **Account write** (1). MCP tools that change a SaaS account, such as adding tracked prompts. A custom server's tools count as writes, so one ask rule on that server covers it.

No SEO skill sends an email or posts in public. Seven say so in terms: `seo-autopilot`, `domain-migration`, `reddit-serp`, `aiseotracker`, `content-coverage`, `youtube-seo` and `parasite-and-pr` (lines cited in the table). The one exception in wording is `seo-autopilot`, which posts its weekly report "to Slack if a channel is configured" (seo-skills:seo/seo-autopilot/SKILL.md:73). If the product later adds sending, OpenBot's sending and posting kinds already ask.

## The options against the evidence

- **A, convert to OpenBot skills.** Feasible as text, since no length limit is evidenced. It loses the files beside the skill (`examples.md` and the two scripts, though both scripts are also printed in full inside their `SKILL.md`: seo-skills:seo/internal-linking/SKILL.md:31, seo-skills:seo/domain-migration/SKILL.md:152). It needs a re-conversion for every upstream release. It leaves the daily Routine dependent on a path nothing in the clone confirms (finding 3 above).
- **B, files in the workspace.** The Bot reads the `SKILL.md` with `computer_read_file` and runs the scripts with `computer_run_command`, both recorded. The `seo/` folder lives in the cloned Site repo in the persistent workspace. The short OpenBot skills still give the `/` menu, the per-Bot assignment in `agents.yaml` and the tool narrowing. Costs: one read per run, a standing instruction that maps the SEO skills' coding-agent vocabulary to OpenBot's tools, and a way to get a pinned copy of the files onto each Bot's computer.
- **C, Claude Agent SDK harness.** As shipped it adds nothing for SEO skills and costs the choice of model provider. Modified to load skills natively, it breaks the requirement in the question. It remains a fair choice of engine under B for an Instance that wants a Claude plan instead of a key, because it still receives OpenBot's own skills and tools.

## Open risks and what could not be verified

1. **Server behaviour is unread.** Unconfirmed: any server-side cap on skill instructions; whether a skill is ever applied without `/`; whether a Routine can invoke one; and how an approval rule's `scope` matches a shell command. Each needs a test on a running Instance. The "what would happen" page is the cheap first check.
2. **The shell is ungated by default.** Until the Ship steps are moved to app tools and a deny rule is in place, a Bot with a write token in its shell could push without an Approval. The token rule (no write credential in the shell) matters more than the string-match deny rule.
3. **The pull-request route is unproven.** Which GitHub tools Composio, Arcade or GitHub's own MCP server offer, whether one can commit many files at once, and how changed files get from the workspace into such a call were not checkable offline. A fallback is a narrow push token for a staging fork only, with the pull request into the Client's repository still opened by the app tool.
4. **Private repositories need a read credential in the shell**, which the Bot can read. A read-only deploy key limits the damage but does not hide it.
5. **Run length.** A command stops at 600 seconds at most, and a note in the app says the server stops a turn it carries on at five minutes (openbot:app/src/lib/approvals.ts:166-173), while a changelog entry says the limit became "five minutes without progress" (openbot:CHANGELOG.md:1636-1638). The first run of `seo-autopilot` crawls the whole Site and ships three fixes (seo-skills:seo/seo-autopilot/SKILL.md:50-57). Whether that fits is unknown.
6. **Computer image contents.** Git, the Node.js version (Scribiz's CLI wants 24+), and whether Playwright's Chromium can be installed were not confirmed. Nor were the default network allowlist, or whether github.com and package registries are reachable under it.
7. **Extra vigilant is too blunt.** Switching it on asks before every change, the Bot's own workspace included (openbot:app/src/components/approvals/ask-first-copy.ts:10-11). Because custom-server tools count as writes, every DataForSEO or Ahrefs lookup would ask too. Targeted rules are needed in its place, and whether a custom server's tools can be marked as reads is not documented.
8. **MCP sign-in may not fit.** AI SEO Tracker's OAuth depends on accepting OpenBot's client registration; Figma's server refuses it (openbot:docs/plugins/mcp-by-url.md:25-27). DataForSEO authenticates with a login and a password, and OpenBot's form takes one key. The addresses of the Ahrefs and DataForSEO servers are in neither clone.
9. **Operators can open the gate.** The asking kinds are open by default, so an Operator may answer "Always allow here". If the product promises an Approval on every Ship step, the Instance needs team rules that ask, the kinds set to "Ask every time", or personal rules switched off (openbot:docs/approvals.md:59-69).
10. **Routine limits.** Twenty enabled per person, none shipped in the package, and no word on how long an Approval raised by an unattended run waits.
11. **Bots do not share a workspace.** Each of the five has its own folder. How they share one clone of the Site and one `seo/` folder (a common git remote, or reads across folders through the shell) is undecided.
12. **The SEO skills steer the Bot.** Two tell it to fetch the newest `SKILL.md` from a vendor's site before acting (seo-skills:seo/linkdr/SKILL.md:28, seo-skills:seo/aiseotracker/SKILL.md:22), and several recommend the author's paid services with a promotional code (seo-skills:seo/linkdr/SKILL.md:37). A file a Bot is told to follow is trusted text, so the copy in the workspace should be pinned, reviewed, and edited where it calls out.
13. **The learned-skill channel was not explored.** It already carries `SKILL.md` folders to Bots on every engine (fact 1). If a hand-written folder can be published into it, that is a fourth option worth a look.
14. **The upstream adapter is unread.** `ag-ui-claude-sdk` is a pip dependency, so its defaults for working directory and settings sources on the full-Bot path are inferred from what OpenBot's subclass does and does not override.
